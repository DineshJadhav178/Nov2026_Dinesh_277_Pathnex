## 1. Centralized Logging – Basic Architecture

### Objective:
Understand how logs move from application servers to a centralized logging platform.

### Architecture:

```text
Application / Linux Server / Kubernetes Pod
                  |
                  v
              Filebeat
          (Log Collection)
                  |
                  v
              Logstash
       (Parsing and Processing)
                  |
                  v
           Elasticsearch
        (Indexing and Storage)
                  |
                  v
               Kibana
       (Search and Visualization)
```

### Key Concepts:

- **Filebeat:** Collects and forwards log files.
- **Logstash:** Processes, parses, and transforms incoming log events.
- **Elasticsearch:** Stores and indexes log events for searching.
- **Kibana:** Provides a user interface for searching logs and building dashboards.

2. What problems occur when logs are stored separately on multiple servers?

## 2. Elasticsearch – Installation and Basic Operations

### Objective:
Understand Elasticsearch and practice basic cluster health and index operations.

### Important APIs:

Check Elasticsearch health:

```bash
curl -X GET "http://localhost:9200/_cluster/health?pretty"
```

Check Elasticsearch node information:

```bash
curl -X GET "http://localhost:9200/_nodes?pretty"
```

List indices:

```bash
curl -X GET "http://localhost:9200/_cat/indices?v"
```

Create a practice index:

```bash
curl -X PUT "http://localhost:9200/sre-logs"
```

Insert a sample log:

```bash
curl -X POST "http://localhost:9200/sre-logs/_doc" \
-H "Content-Type: application/json" \
-d '{
  "timestamp": "2026-11-24T10:30:00",
  "level": "ERROR",
  "service": "payment-service",
  "message": "Database connection timeout"
}'
```

Search logs:

```bash
curl -X GET "http://localhost:9200/sre-logs/_search?pretty"
```

### Important Concepts:

- Index: Logical collection of documents.
- Document: Individual JSON record.
- Shard: Partition of an index.
- Replica: Copy of a primary shard.
- Cluster: Collection of Elasticsearch nodes.
- Mapping: Defines how fields are stored and indexed.

**Important:** For a production setup, configure authentication, TLS, network restrictions, and appropriate Elasticsearch access controls. The above examples assume a local lab with HTTP access enabled.

## 3. Logstash – Log Processing and Parsing

### Objective:
Understand how Logstash collects, filters, and forwards log events.

### Logstash Pipeline Structure:

```text
Input  →  Filter  →  Output
```

### Sample Logstash Configuration:

Create a configuration file:

```bash
sudo mkdir -p /etc/logstash/conf.d
sudo vi /etc/logstash/conf.d/sre-logs.conf
```

Example configuration:

```ruby
input {
  file {
    path => "/var/log/sre-app.log"
    start_position => "beginning"
    sincedb_path => "/tmp/logstash-sincedb"
  }
}

filter {
  grok {
    match => {
      "message" => "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} %{GREEDYDATA:log_message}"
    }
  }
}

output {
  elasticsearch {
    hosts => ["http://localhost:9200"]
    index => "sre-logs-%{+YYYY.MM.dd}"
  }

  stdout {
    codec => rubydebug
  }
}
```

### Sample Log Format:

```text
2026-11-24T10:30:00 ERROR Database connection timeout
2026-11-24T10:35:00 INFO Application started successfully
2026-11-24T10:40:00 WARN High memory utilization detected
```

### Important Concepts:

- Input: Defines the source of log events.
- Filter: Parses and transforms log events.
- Output: Sends processed events to Elasticsearch or another destination.
- Grok: Extracts structured fields from unstructured text.
- Mutate: Modifies event fields.
- Date: Parses timestamps into a consistent date field.

## 4. Filebeat – Log Collection

### Objective:
Understand how Filebeat collects logs from servers and forwards them to Logstash or Elasticsearch.

### Basic Linux Commands:

Check Filebeat service:

```bash
sudo systemctl status filebeat
```

Start Filebeat:

```bash
sudo systemctl start filebeat
```

Enable Filebeat at startup:

```bash
sudo systemctl enable filebeat
```

Restart Filebeat after configuration changes:

```bash
sudo systemctl restart filebeat
```

Validate Filebeat configuration:

```bash
sudo filebeat test config
```

Test Logstash connectivity:

```bash
sudo filebeat test output
```

View Filebeat logs:

```bash
sudo journalctl -u filebeat -f
```

### Sample Filebeat Configuration:

Example for forwarding logs to Logstash:

```yaml
filebeat.inputs:
  - type: filestream
    id: sre-application-logs
    enabled: true
    paths:
      - /var/log/sre-app.log

output.logstash:
  hosts: ["localhost:5044"]
```

## 6. Terraform and Ansible – ELK Infrastructure Automation

### Objective:
Understand the responsibilities of Terraform and Ansible in ELK deployment.

### Terraform Responsibilities:

- Provision EC2 instances.
- Configure security groups and networking.
- Create infrastructure required for Elasticsearch, Logstash, and Kibana.
- Manage infrastructure through configuration files.

### Ansible Responsibilities:

- Install required packages.
- Configure Elasticsearch.
- Install and configure Logstash.
- Install and configure Filebeat.
- Manage service startup and configuration updates.

### Basic Ansible Inventory:

```ini
[elasticsearch]
es-server ansible_host=10.0.1.10

[logstash]
logstash-server ansible_host=10.0.1.20

[kibana]
kibana-server ansible_host=10.0.1.30
```

### Basic Ansible Playbook Example:

```yaml
---
- name: Install and start Filebeat
  hosts: application_servers
  become: true

  tasks:
    - name: Install Filebeat package
      ansible.builtin.package:
        name: filebeat
        state: present

    - name: Enable and start Filebeat
      ansible.builtin.service:
        name: filebeat
        state: started
        enabled: true
```

### Useful Commands:

Check Ansible inventory:

```bash
ansible-inventory -i inventory.ini --list
```

Test connectivity:

```bash
ansible all -i inventory.ini -m ping
```

Run a playbook:

```bash
ansible-playbook -i inventory.ini install-filebeat.yml
```

Validate YAML formatting and indentation before running playbooks.

## 7. ELK Troubleshooting Scenarios – SRE Perspective

### Scenario 1: Logs are not visible in Kibana.

Possible troubleshooting steps:

1. Check whether the application is generating logs.
2. Verify the log file path and file permissions.
3. Check Filebeat service status.
4. Run `filebeat test config` and `filebeat test output`.
5. Check Logstash pipeline configuration and service logs.
6. Verify Elasticsearch cluster health and index creation.
7. Confirm that the Kibana Data View matches the actual index name.

### Scenario 2: Filebeat cannot connect to Logstash.

Check:

```bash
sudo systemctl status filebeat
sudo journalctl -u filebeat -n 100
sudo ss -lntp | grep 5044
```

Verify:

- Logstash is running.
- The Beats input is configured on the expected port.
- Network and security group rules allow the connection.
- Filebeat output host and port are correct.
- TLS settings match on both sides, if enabled.

### Scenario 3: Elasticsearch cluster status is RED.

Check:

```bash
curl -X GET "http://localhost:9200/_cluster/health?pretty"
```

Check shard allocation:

```bash
curl -X GET "http://localhost:9200/_cat/shards?v"
```

Investigate:

- Unassigned primary shards.
- Node availability.
- Disk space and disk watermarks.
- Elasticsearch logs.
- Recent configuration or infrastructure changes.

### Scenario 4: Logs are delayed in Kibana.

Investigate:

- Filebeat publishing delays.
- Logstash queue and processing bottlenecks.
- Elasticsearch indexing and resource utilization.
- Network latency between components.
- Incorrect event timestamps or Kibana time filters.

### Scenario 5: Elasticsearch disk usage is increasing rapidly.

Investigate:

- Index size and daily log volume.
- Unnecessary debug-level logging.
- Index Lifecycle Management policies.
- Retention requirements.
- Shard sizing and replica configuration.

## 8. Elasticsearch Best Practices – ILM, Shards, and Replicas

### Index Lifecycle Management (ILM):

ILM helps manage index lifecycle operations such as:

- Hot phase: Frequently accessed and actively written logs.
- Warm phase: Less frequently accessed logs.
- Cold phase: Older logs that are accessed less frequently.
- Delete phase: Remove data after the configured retention period.

### Shards and Replicas:

- Primary shards distribute index data across the cluster.
- Replica shards provide additional copies of primary shard data.
- Replicas can improve search capacity and provide fault tolerance.
- Replica placement should be planned across separate nodes or failure zones.

### Important Commands:

Check shard allocation:

```bash
curl -X GET "http://localhost:9200/_cat/shards?v"
```

Check node information:

```bash
curl -X GET "http://localhost:9200/_cat/nodes?v"
```

Check index storage:

```bash
curl -X GET "http://localhost:9200/_cat/indices?v"
```

## Important Notes

1. Filebeat is a lightweight log shipper; Logstash is a more flexible processing pipeline.
2. Elasticsearch is responsible for indexing and searching log data.
3. Kibana is used for searching, analyzing, and visualizing Elasticsearch data.

5. Shards distribute data, while replicas provide additional copies for resilience.
6. In production, secure communication with TLS, enable authentication, restrict network access, and protect credentials.
7. Always monitor disk utilization, JVM heap, indexing latency, cluster health, and ingestion delays.
