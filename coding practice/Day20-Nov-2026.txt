## 1. SRE Fundamentals – SLI, SLO, SLA, and Error Budget

### Objective:
Understand how SRE teams measure and maintain service reliability.

### Important Concepts:

- **SLI (Service Level Indicator):** A measurable metric representing service reliability or performance.
- **SLO (Service Level Objective):** The reliability target defined for a service.
- **SLA (Service Level Agreement):** A formal commitment to customers, often including consequences if targets are not met.
- **Error Budget:** The amount of unreliability permitted within a defined period based on the SLO.
- **Toil:** Repetitive manual operational work that provides little lasting value and can often be automated.

### Example:

Assume an application has an SLO of 99.2% availability.

Error Budget:

```text
Error Budget = 100% - SLO

Error Budget = 100% - 99.2%

Error Budget = 0.8%
```

For a 30-day month:

```text
Total time = 30 × 24 × 60

Total time = 43,200 minutes

Allowed downtime = 43,200 × 0.008

Allowed downtime = 345.6 minutes
```

### Python Practice – Error Budget Calculator

```python
slo = 99.2
total_minutes = 30 * 24 * 60

error_budget_percentage = 100 - slo

allowed_downtime = (
    total_minutes * error_budget_percentage / 100
)

print("SLO:", slo, "%")
print("Error Budget:", error_budget_percentage, "%")
print("Allowed Downtime:", allowed_downtime, "minutes")
```

## 2. Linux Production Troubleshooting

### Objective:
Identify CPU, memory, disk, process, and system-level issues using Linux commands.

### CPU Troubleshooting

Check CPU and process utilization:

```bash
top
```

Alternative:

```bash
htop
```

Check CPU information:

```bash
lscpu
```

Find processes consuming the most CPU:

```bash
ps aux --sort=-%cpu | head -10
```

### Memory Troubleshooting

Check memory utilization:

```bash
free -h
```

Find processes consuming the most memory:

```bash
ps aux --sort=-%mem | head -10
```

Check memory information:

```bash
cat /proc/meminfo
```

### Disk Troubleshooting

Check filesystem utilization:

```bash
df -h
```

Check inode utilization:

```bash
df -i
```

Find directory sizes:

```bash
du -sh /var/log
```

Find large directories:

```bash
du -ah /var/log | sort -rh | head -10
```

### Process Troubleshooting

List running processes:

```bash
ps -ef
```

Find a specific process:

```bash
ps -ef | grep nginx
```

Check open ports:

```bash
sudo ss -tulnp
```

### System Log Troubleshooting

View recent system logs:

```bash
sudo journalctl -n 100
```

Follow live system logs:

```bash
sudo journalctl -f
```

Check logs for a particular service:

```bash
sudo journalctl -u nginx -n 100
```

## 4. Monitoring and Observability – Prometheus and Grafana

### Objective:
Understand how infrastructure and application metrics are collected, stored, visualized, and monitored.

### Monitoring Architecture:

```text
Linux / EC2 / Kubernetes / Application
                  |
                  v
             Exporters
                  |
                  v
              Prometheus
          (Metrics Collection)
                  |
          +-------+-------+
          |               |
          v               v
       Grafana        Alertmanager
      Dashboards        Alerting
```

### Important Components:

- **Prometheus:** Collects and stores time-series metrics.
- **Node Exporter:** Exposes Linux system metrics.
- **Grafana:** Creates dashboards and visualizes metrics.
- **Alertmanager:** Handles alert grouping, routing, silencing, and notifications.
- **PromQL:** Query language used to analyze Prometheus metrics.

### Important Metrics:

| Metric | What it indicates |
|---|---|
| CPU utilization | Processor usage |
| Memory utilization | Memory consumption |
| Disk utilization | Filesystem capacity |
| Request rate | Application traffic |
| Error rate | Failed application requests |
| p95 latency | Response time experienced by 95% of requests |
| Pod restarts | Container instability |
| Node health | Kubernetes worker-node condition |

### Sample PromQL Queries:

CPU usage rate:

```promql
100 * (1 - avg by(instance) (
  rate(node_cpu_seconds_total{mode="idle"}[5m])
))
```

Memory utilization:

```promql
100 * (
  1 - node_memory_MemAvailable_bytes
  / node_memory_MemTotal_bytes
)
```

Disk utilization:

```promql
100 * (
  1 -
  node_filesystem_avail_bytes{
    mountpoint="/",
    fstype!~"tmpfs|overlay"
  }
  /
  node_filesystem_size_bytes{
    mountpoint="/",
    fstype!~"tmpfs|overlay"
  }
)
```

### Sample Prometheus Alert Rule:

```yaml
groups:
  - name: infrastructure-alerts
    rules:
      - alert: HighCPUUsage
        expr: |
          100 * (1 - avg by(instance) (
            rate(node_cpu_seconds_total{mode="idle"}[5m])
          )) > 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High CPU usage detected"
          description: "CPU usage is above 85% for 5 minutes."
```

## 5. Application Troubleshooting – HTTP Errors and Latency

### Objective:
Understand common application errors and investigate production application failures.

### Common HTTP Status Codes:

| Status code | Meaning | Common cause |
|---|---|---|
| 500 | Internal Server Error | Application exception |
| 502 | Bad Gateway | Invalid response from upstream |
| 503 | Service Unavailable | Service overloaded or unavailable |
| 504 | Gateway Timeout | Upstream response timeout |

### Useful Commands:

Check application endpoint:

```bash
curl -I http://localhost:8080
```

Check detailed response:

```bash
curl -v http://localhost:8080
```

Check application process:

```bash
ps -ef | grep java
```

Check listening port:

```bash
sudo ss -tulnp | grep 8080
```

Follow application logs:

```bash
tail -f /var/log/application.log
```

Search for errors:

```bash
grep -i "error" /var/log/application.log | tail -50
```

Search for timeout messages:

```bash
grep -i "timeout" /var/log/application.log | tail -50
```

### Application Troubleshooting Approach:

1. Confirm the issue and affected service.
2. Check application health endpoints.
3. Review HTTP response codes.
4. Analyze application logs.
5. Check CPU, memory, and JVM utilization.
6. Verify database connectivity.
7. Check upstream and downstream dependencies.
8. Review recent deployments or configuration changes.
9. Mitigate the issue and validate service recovery.

### Java and JVM Troubleshooting Concepts:

Understand:

- Heap memory.
- Garbage Collection (GC).
- OutOfMemoryError.
- Thread dumps.
- Heap dumps.
- Thread pool exhaustion.
- JVM CPU utilization.

Useful commands:

```bash
jps -l
jstat -gcutil <pid> 1000 5
jcmd <pid> VM.flags
```

Use diagnostic commands carefully in production. Heap dumps and thread dumps can consume resources or contain sensitive application data.

```bash

```

Run:

```bash
./health_check.sh
```

### Python Script – HTTP Health Check

Create a file:

```bash
vi app_health_check.py
```

Add:

```python
import urllib.request
import urllib.error

url = "http://localhost:8080"

try:
    response = urllib.request.urlopen(url, timeout=5)

    if response.status == 200:
        print("Application is healthy")
    else:
        print("Application returned:", response.status)

except urllib.error.HTTPError as error:
    print("HTTP error:", error.code)

except Exception as error:
    print("Application health check failed:", error)
```

Run:

```bash
python3 app_health_check.py
```

## 9. Incident Management, P1/P2 Handling, and RCA

### Objective:
Understand how to respond to production incidents and identify permanent corrective actions.

### Incident Severity:

| Priority | Typical impact |
|---|---|
| P1 | Critical production outage or major business impact |
| P2 | Significant service degradation or partial outage |
| P3 | Limited impact or non-critical functionality issue |
| P4 | Low-impact issue or service request |

Actual severity definitions depend on the organization's incident policy.

### Incident Management Lifecycle:

```text
Alert Detection
      |
      v
Incident Declaration
      |
      v
Impact Assessment
      |
      v
Incident Response
      |
      v
Mitigation
      |
      v
Service Recovery
      |
      v
Root Cause Analysis
      |
      v
Postmortem and Action Items
```

### Example P1 Scenario:

**Scenario:** A production application becomes unavailable and users receive HTTP 503 errors.

Response approach:

1. Acknowledge the alert and confirm the impact.
2. Check application and infrastructure health.
3. Review load balancer target health.
4. Check EC2 or Kubernetes workload availability.
5. Review recent deployments and configuration changes.
6. Engage application, infrastructure, and database teams as required.
7. Apply an approved mitigation or rollback.
8. Validate application recovery.
9. Communicate updates to stakeholders.
10. Prepare RCA and preventive action items.

### Five Whys RCA Example:

**Problem:** Application became unavailable.

1. Why did the application become unavailable?  
   Because application instances became unhealthy.

2. Why did instances become unhealthy?  
   Because memory utilization increased significantly.

3. Why did memory utilization increase?  
   Because application memory consumption increased after a deployment.

4. Why was the memory issue not identified earlier?  
   Because memory trend monitoring and alert thresholds were insufficient.

5. Why were monitoring controls insufficient?  
   Because the deployment validation process did not include appropriate memory-performance checks.

**Corrective Actions:**

- Review application memory behavior.
- Improve memory monitoring and alert thresholds.
- Add deployment performance validation.
- Update operational runbooks.
- Review rollback and release procedures.

### Postmortem Best Practices:

- Focus on facts and timelines.
- Avoid blaming individuals.
- Document customer and business impact.
- Identify root and contributing causes.
- Assign owners and due dates to corrective actions.
- Track preventive actions until completion.

## 10. Capacity Planning, Change Management, and Alerting

### Objective:
Understand how SRE teams maintain stability during high traffic and production changes.

### Capacity Planning:

Capacity planning involves predicting future infrastructure requirements based on:

- Historical traffic patterns.
- CPU and memory utilization.
- Request rate and response time.
- Database connections.
- Storage growth.
- Seasonal and business traffic.
- Expected application growth.

### Change Freeze Concepts:

**Hard Freeze:**
- No routine production changes are permitted.
- Common during critical business events or high-traffic periods.
- Emergency changes follow a separate approval process.

**Cold Freeze:**
- Only approved critical or urgent changes are allowed.
- Non-essential changes are postponed.

These terms can vary by organization, so always follow the actual change-management policy.

### Alerting Best Practices:

- Configure meaningful thresholds.
- Alert on user impact and service symptoms.
- Avoid duplicate and noisy alerts.
- Define severity and escalation paths.
- Include useful troubleshooting information in alerts.
- Review alert effectiveness regularly.

### Practice Questions:

2. Why do organizations implement change freezes?
3. What is the difference between a hard freeze and a cold freeze?
4. How do you reduce alert fatigue?
5. Why should alerts be actionable?
6. How do you prepare infrastructure for seasonal traffic?

## 11. Kafka and Distributed Application Troubleshooting

### Objective:
Understand basic Kafka monitoring and consumer lag troubleshooting.

### Important Kafka Concepts:

- Producer: Publishes messages.
- Broker: Stores and serves messages.
- Topic: Logical category for messages.
- Partition: Divides topic data for scalability.
- Consumer: Reads messages.
- Consumer Group: Coordinates multiple consumers.
- Consumer Lag: Difference between the latest available offset and the consumer's committed progress.

### Common Consumer Lag Causes:

- Slow message processing.
- Insufficient consumer capacity.
- Consumer application errors.
- Broker or network issues.
- Uneven partition distribution.
- Downstream database or service bottlenecks.

### Troubleshooting Approach:

1. Check consumer group lag.
2. Review consumer application logs.
3. Check consumer health and processing rate.
4. Inspect broker health and network connectivity.
5. Review partition distribution.
6. Check downstream dependencies.
7. Scale or optimize consumers where appropriate.

### Practice Questions:

1. What is Kafka consumer lag?
2. What causes consumer lag to increase?
3. How do you troubleshoot a slow consumer?
4. What is a Kafka partition?


- Identify the CPU-intensive process.

Investigate:

- Backend application availability.
- Application listening port.
- Security group connectivity.
- Upstream connection failures.

- Check application errors.
- Review memory and CPU limits.

Investigate:

- Database availability.
- DNS resolution.
- Network connectivity.
- Security group and firewall rules.
- Database connection limits.
- Application connection pool settings.
- Database logs and resource utilization.

### Scenario 5: Disk Utilization Reaches 95%

```bash
df -h

du -sh /var/log
```

Actions:

- Identify large directories and files.
- Check log rotation.
- Review application log growth.
- Follow approved retention and cleanup procedures.

### Scenario 6: High API Response Time

Investigate:

- Request rate and error rate.
- p95 and p99 latency.
- Application CPU and memory.
- JVM garbage collection.
- Database query latency.
- Downstream service response time.
- Network latency.
